# User Input Protocol v1

## Purpose

This contract defines the data package accepted from an end user for an individual digital-twin analysis. It is separate from training, validation, and test datasets.

The system must analyse only modalities actually supplied and QC-accepted. Missing modalities are **unknown/not supplied**, never negative findings.

## Minimal user package

A user can submit a partial package. The minimum useful package is:

- `subject_id`: pseudonymous identifier generated by the application
- `age_years`: age at acquisition (or acquisition date + birth date handled outside the scientific package)
- `hand_side`: `left`, `right`, or `both`
- `acquisition_time`: ISO-8601 timestamp when known
- at least one supported input modality

For every input:

- `input_id`: unique identifier
- `kind`: one of the supported modality kinds
- `uri`: application-managed reference to the uploaded object; raw local paths must not be part of the portable contract
- `acquired_at`: acquisition timestamp when available
- `hand_side`: when applicable
- `region_id`: anatomical region when applicable
- `metadata`: modality-specific metadata
- `provenance`: source/acquisition information

## Supported modalities

### 1. `hand_images`

Required when supplied:
- left/right label
- acquisition timestamp
- image file

Recommended metadata:
- original pixel dimensions
- camera/device
- focal length if known
- scale reference/marker if available
- standardized view (`dorsal`, `palmar`, `radial`, `ulnar`, `thumb`, `other`)
- lighting/exposure information

Quality requirements are enforced by the ingestion/QC layer, not by this document alone.

### 2. `hand_video`

Required when supplied:
- left/right label
- acquisition timestamp
- video file

Recommended:
- frame rate
- resolution
- action/protocol identifier
- camera/device
- calibration information

### 3. `hand_3d`

Accepted representations may include mesh or point cloud.

Required when supplied:
- left/right label
- acquisition timestamp
- 3D object

Recommended:
- metric scale
- coordinate system
- scanner/device
- calibration
- reconstruction method

### 4. `tissue_wsi`

Required when supplied:
- WSI or application-managed reference
- tissue type
- sampling/acquisition metadata
- anatomical region

Recommended:
- stain
- magnification
- pixel size / microns per pixel
- scanner
- block/section identifier
- pathology annotation if available

### 5. `microscopy`

Accepted for microscopy images that are not WSI.

Required:
- image/object
- tissue/cell context
- acquisition metadata

### 6. `single_cell_rna`

Accepted formats should preserve cell-level expression and feature identifiers.

Required:
- expression matrix or equivalent
- cell identifiers
- feature/gene identifiers
- sample/specimen linkage

Recommended:
- tissue/region
- library/protocol
- QC metrics
- cell annotations if available

### 7. `genomics`

Required:
- genomic variant/genotype data or equivalent representation
- genome build/reference
- sample linkage

Recommended:
- VCF/BCF-derived representation
- sequencing/platform metadata
- QC metrics

### 8. `proteomics`

Required:
- protein measurements
- analyte/protein identifiers
- sample/specimen linkage

Recommended:
- assay/platform
- units
- normalization information
- QC metrics

### 9. `epigenetics`

Accepted inputs include DNA methylation and other supported epigenetic measurements.

Required:
- measurement data
- feature/probe/region identifiers
- sample linkage
- reference/build when applicable

Recommended:
- assay/platform
- QC metrics
- normalization information

## Cross-modal identity

When multiple modalities are submitted, the package should explicitly link them through:

`subject_id -> hand_id -> timepoint_id -> region_id/specimen_id -> input_id`

A modality must not be fused with another modality merely because it belongs to the same upload. The system needs an explicit linkage or a declared inability to align the observations.

## Optional clinical/reference information

These are not required for ordinary analysis:

- known diagnosis / disease status
- pathology diagnosis
- treatment history
- laboratory reference values
- independent age/health measurements
- clinician annotations

If supplied, these are reference/evidence data and must be distinguished from model predictions.

## User-facing result contract

The analysis response must distinguish:

1. `observed_inputs` — what the user actually supplied and passed QC
2. `available_analyses` — analyses supported by those inputs
3. `unavailable_analyses` — analyses blocked by missing/invalid inputs
4. `results` — computed outputs
5. `uncertainty` — uncertainty attached to each result where supported
6. `evidence` — provenance/reference evidence used by the model
7. `limitations` — missing modalities, alignment limitations, and validation limitations

The system must never emit `healthy`, `diseased`, `young`, `old`, or an intervention recommendation solely because a corresponding modality is missing.

## What is not required from an ordinary user

A user does **not** need to provide all modalities. In particular, WSI, single-cell RNA, genomics, proteomics, and epigenetics are optional inputs and may be unavailable in normal consumer workflows.

## Scientific boundary

This protocol defines data ingestion and analysis capability, not clinical validity. Biological-age estimation and health/disease classification require separately validated models, reference cohorts, and uncertainty estimates before being presented as scientific or clinical conclusions.
